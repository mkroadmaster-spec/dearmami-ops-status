# 위험 점검표 — 전체 점검을 부탁받았을 때

사용자가 "전체적으로 점검해줘", "위험한 부분이 있는지 봐줘"라고 하면 이 표를 위에서부터 확인한다. 각 항목에 **이미 들어 있는 안전장치**와 **확인 방법**, **사람이 해야 하는 일**을 적었다. 전부 실제로 겪었거나 점검에서 찾은 것이다.

## 1. 데이터가 밖으로 새는 길

| 위험 | 이미 있는 안전장치 | 확인 방법 | 사람이 할 일 |
|---|---|---|---|
| 대시보드 주소는 누구나 열 수 있다 (GitHub Pages 는 공개) | 화면 데이터를 비밀번호로 암호화(PBKDF2 60만 회 → AES-256-GCM) | 주소를 열면 비밀번호 칸이 먼저 나오는가 | **비밀번호를 12자 이상으로.** 짧은 비밀번호는 암호화된 파일을 내려받아 대입해 볼 수 있다. `DASHBOARD_PASSWORD` 를 바꾸고 재배포 |
| 저장소가 Public 이면 Actions 로그·요약도 공개 | Actions 안에서는 금액 미출력(`run_all.py`, `notify.py`, `channel-check`), 오류 문구의 키·계정번호 가림(`mask_secrets`) | 최근 실행 로그를 열어 금액·키가 없는지 본다 | — |
| 예전 실행 기록에 금액·키가 남아 있을 수 있다 | — | `gh run list` 로 오래된 실행 확인 | 로그 삭제 `gh api -X DELETE repos/<R>/actions/runs/<id>/logs`, 요약까지 지우려면 실행 기록 삭제 `…/runs/<id>` |
| 키를 저장소에 커밋 | `config/secrets.env` 는 gitignore, 키는 GitHub Secrets 에만 | `git grep -n -i "secret\|token" -- config` · 이력 검색 | 커밋했다면 그 키를 매체에서 재발급 (`docs/SECURITY-ROTATION.md`) |
| 다른 업체의 정보가 문서·설정에 남아 있음 | 문서에서 다른 업체 식별 정보 제거됨 | 새 업체로 복제한 뒤 `git grep` 으로 이전 업체 이름·도메인·계정번호 검색 | `new_client.py` 실행 후 남은 것을 고친다 |

## 2. 데이터가 조용히 빠지거나 멈추는 길

| 위험 | 이미 있는 안전장치 | 확인 방법 |
|---|---|---|
| 채널 키가 빠진 실행이 다른 채널 데이터를 지움 (실제 사고: 6일치) | `ads`·`ad_campaign` 은 채널 단위로만 교체, 수집 워크플로의 env 통일 | `ads_gap_probe` 로 채널별 빈 날 확인. 수집을 돌리는 워크플로를 새로 만들면 env 를 `daily-collect.yml` 에서 복사 |
| 수집보다 배포가 먼저 돌아 화면이 하루 늦음 | 수집이 성공하면 바로 배포(`pages-deploy` 의 `workflow_run`) | 헤더의 "수집 시각"과 "스냅샷 시각" 순서 |
| GitHub 예약 실행이 몇 시간씩 늦음 | 정각을 피한 cron(06:17 KST) | Actions 의 실제 시작 시각 |
| 60일 동안 커밋이 없으면 GitHub 가 예약 실행을 끔 | 매일 수집 때 예약 워크플로를 다시 켜는 단계(최선 노력) | Actions 탭에 "This scheduled workflow is disabled" 경고가 없는지. 확실히 하려면 두 달에 한 번은 커밋 |
| 수집이 멈췄는데 아무도 모름 | 헤더에 "⚠ 마지막 데이터 N일 전" 배지(3일 이상), 브리핑에 실패 채널 표시 | **텔레그램 알림을 연결했는가** — 없으면 화면을 열기 전까지 모른다 |
| 토큰 만료 | 카페24·카카오·구글 토큰은 DB 에서 자동 갱신 | 구글 OAuth 동의 화면이 「프로덕션」인가(「테스트」면 7일 뒤 만료) · Meta 는 시스템 사용자 토큰인가(일반 토큰은 60일) · 카페24 는 2주 이상 수집이 멈추면 재인증 |
| 주간 리포트 자동 생성 실패 | 원인(없는 키 참조) 수정됨 | 월요일 `cafe24 weekly report` 실행 결과 |
| CSV 로 올리는 매체(GFA·모비온)를 안 올린 기간 | 화면 안내문 | 그 기간은 광고비가 빠져 ROAS 가 높게 보인다고 사용자에게 알린다 |

## 3. 저장 공간

- Neon 무료는 0.5GB. 한도를 넘으면 **저장이 멈춘다.**
- 안전장치: 브리핑에 "DB 용량 85%" 경고(`DB_LIMIT_MB`, 기본 512), 소스별 하루 저장 상한, 0 인 지표 생략.
- 확인: `probe.yml` 에 `script=analytics_probe`, `args=size`
- 대처(사용자에게 고르게 한다. 지우는 것은 되돌릴 수 없다):
  1. `script=prune` (미리보기) → 오래된 **상세** 행(상품·검색어·키워드·소재별)이 몇 줄인지 본다. 일별 합계·매출·채널 합계는 남는다.
  2. 사용자가 기준일에 동의하면 `args=--before YYYY-MM-DD --apply`
  3. 또는 유료 전환, 또는 소스별 상한 축소

## 4. 화면 오류

| 위험 | 안전장치 · 확인 |
|---|---|
| 데이터가 없는 채널에서 "데이터 로드 실패" | `scripts/regress_clicks.js` 를 **빈 데이터 DB** 로 돌린다 (`operations.md` "화면을 고친 뒤 확인하는 법") |
| 정적 페이지에서만 안 되는 기능 (정렬·이전/다음·새 API) | 새 API 는 `export_static.py` 와 `snapGet()` 에 같이 추가. 정렬은 화면에서 |
| 실제 데이터 화면을 직접 못 봄 | 세션에서 배포 주소를 못 여는 경우가 많다. 데모로 확인했으면 사용자에게 그렇게 말하고 캡처를 부탁한다 |
| 리포트 코멘트 분실 | 코멘트는 그 브라우저에만 저장된다. 보고용은 다운로드 파일로 남기라고 알린다 |

## 5. 점검을 마친 뒤 보고하는 법

- 고친 것, 사람이 해야 하는 것(비밀번호·알림·OAuth 게시 상태 등), 선택이 필요한 것(용량 정리)을 나눠서 말한다.
- 데모로만 확인한 것과 실제로 확인한 것을 구분한다.
- 로그·실행 기록 삭제처럼 되돌릴 수 없는 일을 했으면 무엇을 몇 개 지웠는지 적는다.
